# ByteOps AWS Deployment Details

This document explains what has been deployed for ByteOps staging, why each
resource exists, how the application traffic flows, how CI/CD works, and how to
delete or recreate the environment.

## What We Built

ByteOps is deployed as a serverless staging environment in AWS `us-east-1`.
The backend is a FastAPI application running in AWS Lambda. The frontend is a
Next.js application also running in AWS Lambda. Background jobs run in a
separate worker Lambda that receives jobs from SQS.

The deployment uses:

- AWS Lambda for frontend, backend API, and worker compute.
- Lambda Function URLs for public HTTP access.
- Amazon ECR for Docker images used by Lambda.
- AWS Secrets Manager for runtime application secrets.
- Amazon SQS for async and scheduled job delivery.
- Amazon EventBridge Scheduler for recurring hourly jobs.
- IAM roles and policies for least-needed runtime access.
- CloudWatch Logs for Lambda logs.
- CloudWatch Alarms and SNS for alerting.
- AWS Budgets for a simple monthly cost guard.
- Terraform for infrastructure as code.
- GitHub Actions for CI and automated staging deployment.
- An S3 Terraform backend for remote Terraform state.

## Application Components

### Frontend Lambda

Resource name: `byteops-staging-frontend`

Purpose:

- Serves the Next.js user interface.
- Provides the pages users open in the browser.
- Sends API requests to the backend Lambda URL.
- Uses the public Clerk publishable key at build time for browser auth flows.

Why Lambda:

- No server to manage.
- Low cost for staging because it only runs when requested.
- Easy image-based deployment through ECR.

Important settings:

- Package type: Docker image.
- Memory: `2048 MB`.
- Timeout: `60 seconds`.
- Public access: Lambda Function URL with `authorization_type = "NONE"`.
- Invoke mode: `BUFFERED`.
- Logs: `/aws/lambda/byteops-staging-frontend`.

### Backend API Lambda

Resource name: `byteops-staging-api`

Purpose:

- Runs the FastAPI API.
- Handles auth-protected app routes.
- Handles OAuth start and callback routes for tools like Gmail, Calendar,
  GitHub, Slack, Jira, Trello, and Dropbox.
- Reads application secrets from AWS Secrets Manager.
- Sends async sync jobs to SQS.

Why Lambda:

- Fits the requested serverless backend plan.
- Avoids managing EC2, ECS services, or load balancers for staging.
- Scales down to zero when idle.

Important settings:

- Package type: Docker image.
- Memory: `2048 MB`.
- Timeout: `300 seconds`.
- Public access: Lambda Function URL with `authorization_type = "NONE"`.
- Invoke mode: `RESPONSE_STREAM`.
- CORS allows browser requests.
- Logs: `/aws/lambda/byteops-staging-api`.

Important environment variables:

- `AWS_SECRETS_ID`: tells the app which Secrets Manager secret to load.
- `SYNC_QUEUE_URL`: tells the API where to send background jobs.
- `FRONTEND_URL`: used when redirecting users back to the frontend.
- `BACKEND_CORS_ORIGINS`: allows the frontend origin.
- `ENABLE_SCHEDULER=false`: prevents in-process scheduling in API Lambda.
- `INITIALIZE_DATABASE=false`: avoids automatic schema creation at Lambda start.
- `DEBUG=false`: disables debug behavior in staging.

### Worker Lambda

Resource name: `byteops-staging-worker`

Purpose:

- Processes SQS jobs outside the HTTP request path.
- Runs immediate sync jobs after OAuth connections.
- Runs periodic sync jobs.
- Runs periodic workflow jobs.

Why a separate worker:

- Keeps browser/API requests fast.
- Lets long-running sync work use a longer timeout.
- Lets failures retry through SQS instead of failing the user request.

Important settings:

- Package type: Docker image.
- Memory: `2048 MB`.
- Timeout: `900 seconds`.
- Trigger: SQS event source mapping from `byteops-staging-jobs`.
- Batch size: `5`.
- Maximum batching window: `5 seconds`.
- Partial failure reporting: enabled through `ReportBatchItemFailures`.
- Logs: `/aws/lambda/byteops-staging-worker`.

## Container Images And ECR

Three ECR repositories are used:

- `byteops-staging-api`
- `byteops-staging-worker`
- `byteops-staging-frontend`

Purpose:

- Store Docker images for each Lambda function.
- Let Terraform point each Lambda at an immutable image URI.
- Let GitHub Actions build and deploy one image tag per commit.

Important settings:

- Image tags are immutable.
- Image scanning on push is enabled.
- Lifecycle policy keeps the latest 20 images.
- `force_delete = true` is enabled so the destroy script can remove non-empty
  repositories.

Why separate repositories:

- API, worker, and frontend have different Dockerfiles and runtime behavior.
- Separate repositories make deployments and rollbacks easier to reason about.

## Secrets Manager

Secret name: `byteops-staging/application`

Purpose:

- Stores app secrets and runtime configuration that should not be hard-coded in
  Terraform, GitHub Actions, or source code.
- Holds database URL, Clerk secrets, LLM provider keys, OAuth client IDs,
  OAuth client secrets, redirect URIs, frontend URL, and CORS origin values.

How the app uses it:

1. Lambda receives `AWS_SECRETS_ID=byteops-staging/application`.
2. Backend config loads the JSON secret from Secrets Manager.
3. Values are copied into process environment variables.
4. App settings read those values through Pydantic settings.

Why Secrets Manager:

- Keeps sensitive values out of Git.
- Gives AWS IAM-controlled access to only the Lambdas that need it.
- Lets the local deploy script synchronize `.env` into AWS without committing
  secrets.

Important deletion behavior:

- `recovery_window_in_days = 0` is configured for staging so destroy can
  recreate the same secret name immediately.
- This is convenient for staging, but production should usually keep a recovery
  window.

## Database

No AWS RDS or DynamoDB database is currently created by Terraform.

Current behavior:

- The application uses the PostgreSQL URL stored in `.env` and synchronized into
  Secrets Manager.
- The code expects a PostgreSQL-compatible async SQLAlchemy URL.
- The comments in config mention Neon PostgreSQL, so the current deployment is
  using an external PostgreSQL service rather than AWS-managed RDS.

Why RDS was not created yet:

- The requested first AWS deployment prioritized Lambda, SQS, and Secrets
  Manager.
- Moving the database into RDS requires migration planning, backups, network
  design, credentials rotation, and possible VPC Lambda configuration.

Why DynamoDB is not used:

- The current codebase is written around SQLAlchemy models and PostgreSQL.
- Moving to DynamoDB would require application-level data model changes.

## SQS Queues

### Main Jobs Queue

Resource name: `byteops-staging-jobs`

Purpose:

- Decouples backend API requests from background sync and workflow processing.
- Receives jobs from API Lambda and EventBridge Scheduler.
- Triggers the worker Lambda.

Important settings:

- Visibility timeout: `900 seconds`.
- Message retention: `345600 seconds` / 4 days.
- Dead-letter policy: after 3 failed receives, messages go to the DLQ.

Why the visibility timeout matches worker timeout:

- Worker Lambda can run for up to 900 seconds.
- The message should stay invisible while the worker is processing it.

### Dead-Letter Queue

Resource name: `byteops-staging-jobs-dlq`

Purpose:

- Stores jobs that fail repeatedly.
- Prevents one bad message from retrying forever.
- Gives operators a place to inspect failed payloads.

Important settings:

- Message retention: `1209600 seconds` / 14 days.

## EventBridge Scheduler

Two schedules are configured:

- `byteops-staging-periodic-sync`
- `byteops-staging-periodic-workflows`

Purpose:

- Send scheduled jobs into SQS every hour.
- Replace the app's local in-process scheduler in the Lambda environment.

Why EventBridge Scheduler:

- Lambda containers are not always running.
- A scheduler inside the API Lambda would be unreliable because Lambda scales to
  zero and containers can be recycled.
- EventBridge Scheduler is AWS-managed and invokes on time without needing a
  running server.

Job payloads:

```json
{ "job_type": "periodic_sync_all" }
```

```json
{ "job_type": "periodic_workflows_all" }
```

## IAM Roles And Permissions

### GitHub Deploy Role

Resource name: `byteops-staging-github-deploy`

Purpose:

- Allows GitHub Actions to deploy to AWS without storing long-lived AWS access
  keys in GitHub secrets.

How it works:

1. GitHub Actions receives an OIDC token from GitHub.
2. AWS validates the token using the GitHub OIDC provider.
3. AWS allows role assumption only for:
   `repo:Rafayktk/ByteOps2.0:ref:refs/heads/main`.
4. The workflow gets temporary AWS credentials.

Current policy:

- `AdministratorAccess` is attached as a bootstrap deployment policy.

Why this is acceptable for staging bootstrap:

- It made the first full Terraform deployment possible quickly.
- It avoids repeated permission tuning while the resource set is still changing.

Production recommendation:

- Replace this with a resource-scoped deploy policy.

### API And Frontend Lambda Role

Resource name: `byteops-staging-lambda`

Purpose:

- Used by API and frontend Lambdas.
- Allows writing CloudWatch logs.
- Allows reading the application secret.
- Allows sending SQS messages to the jobs queue.

Why frontend also has the same role:

- The frontend Lambda receives `AWS_SECRETS_ID`.
- The shared role keeps the current staging Terraform simpler.

Production recommendation:

- Split frontend and API roles so the frontend has only the permissions it
  actually needs.

### Worker Lambda Role

Resource name: `byteops-staging-worker`

Purpose:

- Allows worker Lambda to write CloudWatch logs.
- Allows worker Lambda to read the application secret.
- Allows worker Lambda to receive, delete, and inspect messages from the jobs
  queue.

### Scheduler Role

Resource name: `byteops-staging-scheduler`

Purpose:

- Allows EventBridge Scheduler to send messages to SQS.

Why a role is needed:

- Scheduler is an AWS service. It must assume an IAM role before it can publish
  messages into the queue.

## Alerts And Budget

Resource name: `byteops-staging-alerts`

Purpose:

- Receives CloudWatch alarm notifications.
- Can send email notifications if `alert_email` is configured.

Current behavior:

- If `alert_email` is blank, no email subscription is created.

### API Error Alarm

Resource name: `byteops-staging-api-errors`

Purpose:

- Alarms when the API Lambda has one or more errors in a 5-minute period.

### DLQ Messages Alarm

Resource name: `byteops-staging-dlq-messages`

Purpose:

- Alarms when there is at least one visible message in the DLQ.
- This means background jobs are failing repeatedly and need inspection.

### AWS Budget

Resource name: `byteops-staging-monthly`

Purpose:

- Creates a monthly cost budget for staging.
- Default limit is `$25`.
- Sends forecast notifications only if `alert_email` is configured.

## GitHub Actions CI/CD

### CI Workflow

File:

```text
.github/workflows/ci.yml
```

Purpose:

- Runs backend tests.
- Runs frontend tests.
- Builds the frontend.

Triggers:

- Pull requests.
- Pushes to `main`.

What it proves:

- Backend Python tests pass.
- Frontend Vitest tests pass.
- Frontend production build succeeds.

### Deploy Staging Workflow

File:

```text
.github/workflows/deploy-staging.yml
```

Purpose:

- Builds Docker images.
- Pushes images to ECR.
- Runs Terraform apply.
- Smoke-tests the live AWS deployment.

Triggers:

- Manual `workflow_dispatch`.
- Pushes to `main` when backend, frontend, staging Terraform, or the deploy
  workflow changes.

Deployment steps:

1. Check out repository.
2. Assume AWS IAM role through GitHub OIDC.
3. Log in to ECR.
4. Build API image.
5. Build worker image.
6. Build frontend image.
7. Push all images to ECR using the Git commit SHA as the tag.
8. Run `terraform init`.
9. Run `terraform apply -auto-approve`.
10. Read Terraform outputs.
11. Smoke test API health.
12. Smoke test API root.
13. Smoke test frontend root.
14. Confirm `/dashboard` redirects with `307`.

Why GitHub Actions is the CI/CD engine:

- Terraform defines what AWS should look like.
- GitHub Actions decides when to build and apply it.
- AWS IAM OIDC avoids storing AWS access keys in GitHub.

## Runtime Request Flow

### Frontend Page Load

1. User opens the frontend Lambda URL.
2. AWS invokes `byteops-staging-frontend`.
3. The Next.js server returns HTML and assets.
4. Browser loads the app.
5. Browser uses Clerk for user authentication.

### API Request Flow

1. Frontend sends a request to the API Lambda URL.
2. AWS invokes `byteops-staging-api`.
3. FastAPI route runs.
4. Auth-protected routes verify Clerk JWTs.
5. Backend reads secrets from Secrets Manager if not already loaded.
6. Backend reads or writes PostgreSQL data through the configured database URL.
7. Backend returns JSON or streaming response.

### OAuth Connection Flow

1. User clicks connect for a provider.
2. Frontend calls the backend OAuth start route.
3. Backend redirects user to the provider authorization screen.
4. Provider redirects back to the exact callback URL.
5. Backend exchanges the auth code for tokens.
6. Backend stores the connection in PostgreSQL.
7. Backend queues immediate sync work through SQS when applicable.
8. User is redirected back to the frontend.

Important:

- Google and Atlassian errors shown in the browser are provider configuration
  errors.
- The exact AWS callback URLs must be registered in those provider consoles.
- AWS cannot register these URLs inside Google, Atlassian, Slack, GitHub,
  Dropbox, or Trello accounts.

### Background Job Flow

1. API or EventBridge Scheduler sends a JSON message to SQS.
2. SQS invokes the worker Lambda through event source mapping.
3. Worker parses `job_type`.
4. Worker runs the matching sync or workflow function.
5. On success, SQS deletes the message.
6. On failure, Lambda reports the failed message.
7. SQS retries the message.
8. After 3 failed receives, SQS moves it to the DLQ.
9. CloudWatch alarm fires if DLQ has messages.

## What We Did Not Use Yet

### S3 Static Hosting

Not used for frontend hosting.

Reason:

- The current frontend runs as a Next.js server in Lambda, not as static files.
- This keeps server-rendering and redirects working without redesigning the app.

S3 is used only for Terraform remote state.

### DynamoDB

Not used.

Reason:

- The application uses PostgreSQL models through SQLAlchemy.
- DynamoDB would require a data model rewrite.

### RDS

Not used yet.

Reason:

- The current database is an external PostgreSQL URL stored in Secrets Manager.
- RDS migration should be planned separately.

### API Gateway

Not used.

Reason:

- Lambda Function URLs are simpler and cheaper for staging.
- API Gateway can be added later for custom domains, stronger throttling,
  authorizers, WAF, and more advanced routing.

### CloudFront

Not used.

Reason:

- Staging currently uses direct Lambda Function URLs.
- CloudFront can be added later for custom domain, caching, TLS control, and
  edge performance.

## Known Limitations And Future Improvements

- OAuth providers must be manually updated with exact callback URLs.
- Lambda Function URLs may change after destroy/recreate.
- The database is not managed by this Terraform stack.
- GitHub deploy role currently uses `AdministratorAccess` for staging bootstrap.
- Frontend and API currently share a Lambda IAM role.
- There is no custom domain yet.
- There is no WAF or CloudFront layer yet.
- Secrets Manager uses immediate deletion for staging convenience.
- Alert emails are active only if `alert_email` is configured.

Recommended next improvements:

1. Move PostgreSQL into AWS RDS or explicitly document the chosen external DB.
2. Replace deploy `AdministratorAccess` with scoped IAM permissions.
3. Add custom domains for frontend and API.
4. Add CloudFront in front of the frontend.
5. Split frontend and API IAM roles.
6. Add RDS backups and migration workflow if RDS is adopted.
7. Add provider-specific OAuth smoke tests after callbacks are registered.

## Operational Checklist

After a normal GitHub deployment:

1. Confirm CI is green.
2. Confirm Deploy Staging is green.
3. Open the frontend URL.
4. Open `/health` on the API URL.
5. Confirm Terraform plan has no drift.
6. Check CloudWatch logs if a page or API route fails.

After a full destroy and redeploy:

1. Run `.\scripts\deploy-staging.ps1`.
2. Capture the new frontend and API URLs if AWS generated new ones.
3. Register new OAuth callback URLs in provider consoles.
4. Confirm Secrets Manager has the new `FRONTEND_URL`,
   `BACKEND_CORS_ORIGINS`, and provider redirect URIs.
5. Run live smoke tests.
